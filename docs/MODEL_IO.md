## 1. 모델이 하는 일

**애프터스테이트 가치 모델**이다. 블록 하나를 놓을 때마다 Java가 도달 가능한 모든 배치(RULES 14장)를 찾고, 각 배치를 놓은 **직후의 상태(애프터스테이트)** 를 **결정 시점의 상대 상태**와 함께 모델에 한꺼번에 넣는다. 모델은 배치마다 점수 하나를 돌려주고, Java는 점수가 높은 배치부터 실행 가능 여부를 확인해 고른다.

- 한 번 호출에 후보 `N`개(보통 40개 안팎, 홀드 포함)를 **배치(batch)** 로 넣는다. 상대 상태는 후보와 상관없이 같으므로 `N`번 반복해 넣는다.
- 모델은 규칙을 몰라도 된다. 후보는 모두 Java가 만든, 실제로 갈 수 있는 배치다.
- **락 아웃(RULES 7장 3단계)이 되는 배치는 후보에서 뺀다.** 지는 수이므로 모델에 넣지 않는다. Python 학습 쪽도 같은 후보 집합을 쓴다.

## 2. 모델에 넣는 상태

### 2.1 애프터스테이트

블록을 놓고 RULES 7장 **1~7단계**까지 진행한 상태다. 즉 줄 삭제, 공격 계산, 상쇄까지는 반영하고, **8단계의 가비지 상승은 반영하지 않는다**(구멍 열이 무작위라서, PLAN 9.1).

| 항목 | 뜻 |
|---|---|
| 보드 | 줄 삭제 후, 가비지 상승 전의 24 × 10 보드 |
| `queue` | 이 배치 뒤에 **이미 알고 있는** 블록들. 다음에 나올 블록이 첫 번째. 결정 시점에 보이던 미리보기 5개 중 아직 쓰지 않은 것 |
| `hold` | 이 배치 뒤의 홀드 칸 (없으면 `null`) |
| `combo` | 이 배치 **뒤**의 콤보 (RULES 9.3을 적용한 뒤, 없으면 −1) |
| `b2b` | 이 배치 **뒤**의 B2B 연속 여부 (RULES 9.3을 적용한 뒤) |
| `lines` | 이 배치가 지운 줄 수 (0~4) |
| `attack` | 이 배치의 공격 줄 수, **상쇄 전** (RULES 9.3) |
| `pending` | 상쇄한 **뒤** 남은 대기 가비지 줄 수의 합 (RULES 10.1) |

`queue`를 정하는 방법:

| 이 배치 | 결정 시점 미리보기 `p1..p5` | 배치 뒤 `queue` |
|---|---|---|
| 홀드 안 씀 | 현재 블록을 놓음 | `p1, p2, p3, p4, p5` (5개) |
| 홀드 씀, 홀드가 차 있었음 | 홀드 블록을 놓고 현재 블록이 홀드로 | `p1, p2, p3, p4, p5` (5개) |
| 홀드 씀, 홀드가 비어 있었음 | `p1`을 놓고 현재 블록이 홀드로 | `p2, p3, p4, p5` (4개) |

배치 뒤에 새로 공개될 6번째 블록은 **넣지 않는다**(아직 모르는 정보). 미리보기를 5개보다 길게 알고 있더라도(예: 엔진의 가방 대기열) 앞 5개만 쓴다.

### 2.2 상대 상태

배치를 고르는 순간 화면에 보이는 상대의 상태다. 블록 동기 모드(RULES 12.2)에서는 턴 시작 시점, 실제 게임에서는 AI가 배치를 고르는 순간이다.

| 항목 | 뜻 |
|---|---|
| 보드 | 상대가 마지막으로 고정한 뒤(가비지 상승 포함)의 24 × 10 보드. 떨어지고 있는 블록은 넣지 않는다 |
| `pending` | 상대가 받을 대기 가비지 줄 수의 합 |
| `combo` | 상대의 지금 콤보 (없으면 −1) |
| `b2b` | 상대의 지금 B2B 연속 여부 |
| `hold` | 상대의 홀드 칸 (없으면 `null`) |

상대가 없으면(1인용) 빈 보드, `pending` 0, `combo` −1, `b2b` false, `hold` 없음으로 본다. 그러면 상대 입력(3.3, 3.4)은 모두 0이다.

## 3. 입력 텐서

입력은 **정확히 네 개**다. 이름, 자료형(float32), 모양이 정확히 같아야 한다. 첫 번째 축 `N`은 후보 수이고 크기가 정해져 있지 않다(dynamic axis). Java는 모델을 불러올 때 이 넷을 모두 확인하고, 다르면 그 모델을 쓰지 않는다.

| 입력 | 모양 | 내용 |
|---|---|---|
| `board` | `[N, 24, 10]` | 후보의 애프터스테이트 보드 (3.1) |
| `features` | `[N, 48]` | 후보의 애프터스테이트 특징 (3.2) |
| `opp_board` | `[N, 24, 10]` | 상대 보드 (3.3). `N`개 모두 같은 값 |
| `opp_features` | `[N, 10]` | 상대 특징 (3.4). `N`개 모두 같은 값 |

### 3.1 `board`: float32 `[N, 24, 10]`

- `board[n][r][c]` = 애프터스테이트 보드의 `r`행 `c`열이 차 있으면 `1.0`, 비어 있으면 `0.0`
- `r = 0`이 맨 위(숨김 영역 포함), `r = 23`이 바닥. RULES 1장과 같은 좌표
- 칸의 종류(블록 색, 가비지)는 구분하지 않는다

### 3.2 `features`: float32 `[N, 48]`

| 위치 | 개수 | 값 |
|---|---|---|
| 0 ~ 34 | 35 | `queue`의 앞 5칸을 칸마다 7개 원-핫으로. 칸 `k`(0~4)의 블록이 `I J L O S T Z` 중 `j`번째(0~6)면 `features[7k + j] = 1`. 블록이 없는 칸은 7개 모두 0 |
| 35 ~ 41 | 7 | `hold` 원-핫 (`I J L O S T Z` 순서). 비었으면 모두 0 |
| 42 | 1 | `combo + 1` (콤보가 없으면 0) |
| 43 | 1 | `b2b`면 1, 아니면 0 |
| 44 | 1 | `lines` |
| 45 | 1 | `attack` |
| 46 | 1 | `pending` |
| 47 | 1 | 이번 고정에서 가비지가 올라오면 1: `lines = 0`이고 `pending > 0`. 아니면 0 |

### 3.3 `opp_board`: float32 `[N, 24, 10]`

상대 보드(2.2)를 3.1과 같은 방법으로 바꾼 것이다. 후보 `N`개에 같은 값을 넣는다.

### 3.4 `opp_features`: float32 `[N, 10]`

| 위치 | 개수 | 값 |
|---|---|---|
| 0 | 1 | 상대 `pending` |
| 1 | 1 | 상대 `combo + 1` (콤보가 없으면 0) |
| 2 | 1 | 상대 `b2b`면 1, 아니면 0 |
| 3 ~ 9 | 7 | 상대 `hold` 원-핫 (`I J L O S T Z` 순서). 비었으면 모두 0 |

공통 규칙:

- 모든 값은 **정수를 그대로 float32로 바꾼 것**이다. 나누기, 로그 같은 정규화는 입력을 만들 때 하지 않고 **모델 안에서** 한다. 그래야 Java와 Python의 입력이 비트 단위로 같다.
- 블록 순서 `I J L O S T Z`는 RULES 5.3의 기준 순서이자 Java `PieceType` 선언 순서다.

## 4. 출력

- `value`: float32 `[N, 1]`(정확히 이 모양. `[N]`으로 내보내면 Java가 거부한다). 클수록 좋은 배치다.
- **`value`는 그 배치를 고르는 데 쓰는 최종 점수**다. Java는 다른 값을 더하지 않고 `value`만으로 순위를 매긴다. 따라서 "즉시 보상 + γ·V"로 고르도록 학습했다면(TRAINING.md 3.1), **즉시 보상과 γ를 모델 안에서 더해 내보낸다.** 즉시 보상에 쓰는 지운 줄 수와 공격은 입력 `features[44]`, `features[45]`에 있다.
- 값의 범위는 모델마다 다를 수 있다. 게임 화면에 "형세 점수"로 보여 줄 때의 정규화 방법은 아직 정하지 않았다.

## 5. 모델 꼬리표 (ONNX metadata)

ONNX 파일의 `metadata_props`에 다음 키를 넣는다. Java는 모델을 불러올 때 필수 키를 확인하고, 맞지 않으면 **그 모델을 쓰지 않고 휴리스틱 AI로 대신한다**.

| 키 | 필수 | 예 | 뜻 |
|---|---|---|---|
| `tetris.model_io` | 필수 | `2` | 이 문서의 형식 버전. Java가 아는 버전과 같아야 한다 |
| `tetris.rules` | 필수 | `0.3` | 학습에 쓴 규칙 버전(RULES.md). Java의 규칙 버전과 같아야 한다. 규칙이 바뀌면 모델을 다시 학습해야 한다 |
| `tetris.persona` | 선택 | `attacker` | 페르소나 이름(8장). 없으면 `neutral`로 본다. Java는 이 값을 이름 표시와 파일 선택에만 쓰고 검사하지는 않는다 |
| `tetris.stage` | 선택 | `gen-012` | 학습 단계. 난이도별 체크포인트를 구분할 때 쓴다 |
| `tetris.description` | 선택 | 자유 문장 | 사람이 읽는 설명 |

## 6. 내보내기 규칙 (Python)

- 입력 이름 `board`, `features`, `opp_board`, `opp_features`, 출력 이름 `value`. `N` 축은 모두 dynamic axis로 둔다.
- ONNX opset **17**로 내보낸다(PyTorch: `torch.onnx.export(..., opset_version=17, dynamic_axes=...)`). Java의 ONNX Runtime 1.30이 읽을 수 있는 범위다.
- 출력이 `[N]`으로 줄어들지 않도록 마지막에 `[N, 1]` 모양을 유지한다(PyTorch에서 `squeeze()`를 하지 않는다).
- 내보낸 뒤 Python의 `onnxruntime`으로 한 번 불러 `fixtures/model_io/`의 입력으로 돌려 보고, 꼬리표와 출력 모양을 확인한다.

### 6.1 실행 플랫폼 (Java)

ONNX Runtime 1.30 Java jar에는 **Windows x64, Linux x64·arm64, macOS Apple Silicon**용 실행 파일만 들어 있다. Intel Mac 등 다른 플랫폼에서는 `OnnxScorer.isAvailable()`이 false이고, 게임은 휴리스틱 AI로 대신하며, ONNX 테스트는 건너뛴다.

## 7. 검증 (공통 픽스처)

[fixtures/model_io/](../fixtures/model_io/)에 가중치를 직접 정한 **시험용 선형 모델** `linear_v2.onnx`와 사례 파일이 있다. 사례 형식은 [FIXTURES.md](FIXTURES.md) 5.9.

| 사례 | 확인하는 것 |
|---|---|
| `encode` | 애프터스테이트 → `board`, `features` 텐서. Java 인코더와 Python 인코더가 같은 값을 만드는지 |
| `encode_opponent` | 상대 상태 → `opp_board`, `opp_features` 텐서 |
| `run` | 애프터스테이트 여러 개와 상대 상태 → 모델 출력. **Python ONNX Runtime이 계산한 값**을 기대값으로 적고 Java ONNX Runtime이 같은 값(오차 1e-5 이내)을 내는지. 상대가 없는 사례도 있다 |
| `metadata` | 꼬리표 읽기와 버전 확인 |

Java가 **거부해야 하는** 모델도 함께 있다(`OnnxScorerTest`): 규칙 버전이 틀린 `linear_v2_wrong_rules.onnx`, 형식 버전이 틀린 `linear_v2_wrong_model_io.onnx`, 출력이 `[N]`인 `linear_v2_flat_output.onnx`, 꼬리표는 형식 2인데 입력이 형식 1처럼 두 개뿐인 `linear_v2_two_inputs.onnx`.

시험용 모델과 사례 파일은 [python/tools/make_test_model.py](../python/tools/make_test_model.py)로 다시 만들 수 있다. 같은 버전의 패키지로 만들면 바이트 단위로 같은 파일이 나온다.

학습 루프와 같은 구조(합성곱, 보드 통계, 보상 항목, 기준 평가, 임베딩)의 **작은 가치망** `value_tiny.onnx`와 사례 `value_tiny.json`도 있다. 실제로 내보내는 모델의 연산을 Java ONNX Runtime이 Python과 같은 값으로 실행하는지 확인한다. [python/tools/make_value_fixture.py](../python/tools/make_value_fixture.py)로 만들며 PyTorch가 필요하다.

## 8. 페르소나 모델 (PLAN 9.3)

학습할 때는 **신경망 하나를 여러 AI가 공유**하고, AI마다 작은 **페르소나 임베딩**(학습되는 벡터)을 따로 둔다. 임베딩은 신경망 안쪽 입력으로 들어가며, AI마다 보상 비율(공격·안전·T-spin 등)이 다르다(TRAINING.md 4.3, 9장).

- **내보낼 때는 페르소나마다 임베딩을 상수로 고정한 ONNX 파일을 따로 만든다.** 그래서 입력은 이 문서의 형식 2 그대로이고, Java는 페르소나에 맞는 파일을 고르기만 하면 된다.
- 파일 이름: `value_<페르소나>_<단계>.onnx` (예: `value_attacker_gen-120.onnx`). 꼬리표 `tetris.persona`, `tetris.stage`에 같은 값을 넣는다.
- 임베딩 값 자체는 클러스터링 분석(PLAN 8장)에 쓰며 Java에는 필요 없다. 학습 쪽 기록에 남긴다.

## 9. 승률 예측망 형식 `winprob-1` (PLAN 9.5)

과제 기능 2번의 실시간 예상 승률은 가치 모델과 따로 학습한 **승률 예측망**(두 플레이어의 상태 → P1이 이길 확률)으로 만든다. 입력과 출력이 형식 2와 전혀 달라서 형식 버전을 따로 매긴다: **`winprob-1`**. 학습 방법은 [TRAINING.md](TRAINING.md) 10장이다. 이 형식을 바꿀 때도 **이 장 → `fixtures/winprob/` → Python·Java 코드** 순서로 고친다.

### 9.1 모델이 하는 일

- 대전 중 어느 순간이든 두 플레이어의 상태를 넣으면 **P1의 기대 점수** `p = P(P1 승) + 0.5 · P(무승부)`를 돌려준다. 무승부는 드물어서(학습 자료의 약 1%, 모두 같은 턴에 둘 다 진 판) 사실상 P1이 이길 확률이다. 승률 막대는 P1에 `p`, P2에 `1 − p`를 보여 주면 된다.
- 한 번 호출에 상태 쌍 `N`개를 배치로 넣을 수 있다. 게임 화면에서는 보통 `N = 1`이다.
- **자리 대칭:** 두 플레이어를 바꿔 넣으면 출력이 `1 − p`가 되어야 한다. 두 자리의 규칙이 같기 때문이다(같은 블록 순서, 가비지 구멍 난수는 자리마다 다르지만 분포는 같다, RULES 5.2·12.2). 이 형식의 모델은 이 성질을 구조로 지킨다(TRAINING.md 10.3). Java는 이 성질에 기대지 않고 출력을 그대로 쓴다.

### 9.2 모델에 넣는 상태

플레이어마다 **결정 시점의 상태**를 넣는다. 지금 놓을 블록을 아직 놓지 않은 상태로, 기록 `match-1`의 `state`(TRAINING.md 7.3)와 같고, 게임에서는 그 플레이어 `GameModel`의 지금 상태다.

| 항목 | 뜻 |
|---|---|
| 보드 | 마지막으로 고정한 뒤(가비지 상승 포함)의 24 × 10 보드. 떨어지고 있는 블록은 넣지 않는다 |
| `current` | 지금 놓을 차례인 블록 |
| `queue` | 미리보기 5개. 다음에 나올 블록이 첫 번째 |
| `hold` | 홀드 칸 (없으면 `null`) |
| `combo` | 지금 콤보 (없으면 −1) |
| `b2b` | 지금 B2B 연속 여부 |
| `pending` | 받을 대기 가비지 줄 수의 합 |

- **두 플레이어의 블록 순서는 같지만 진행 정도가 다를 수 있다**(RULES 5.2). 블록 동기 모드에서도 빈 홀드에 처음 넣는 쪽은 가방이 한 칸 더 나아가 미리보기가 한 칸 어긋나고, 실제 게임에서는 두 플레이어의 속도가 달라 더 크게 어긋난다. 그래서 플레이어마다 `current`와 `queue`를 따로 넣는다.
- **턴 번호는 넣지 않는다.** ① 실제 게임(가상 시간 모드)에는 두 플레이어에 공통인 턴이 없다(놓은 블록 수가 서로 다르다). ② 위 상태가 앞날을 정하는 정보를 거의 다 담는다. 남은 무작위성은 가비지 구멍 열과 두 플레이어가 앞으로 둘 수다. ③ 넣으면 턴 상한 무승부(RULES 12.2) 같은 학습 자료만의 성질을 배울 수 있다. 판의 단계별 정확도는 평가에서 따로 잰다(TRAINING.md 10.5).
- 대기 가비지는 덩어리 구성 없이 줄 수의 합만 넣는다. 기록의 `state`에 합만 있기 때문이다.
- 어느 한쪽이라도 끝난 판의 상태는 넣지 않는다. 결과가 곧 답이다(9.6).

### 9.3 입력 텐서

입력은 **정확히 네 개**다. 모두 float32이고, 첫 축 `N`은 크기가 정해져 있지 않다(dynamic axis). Java는 모델을 불러올 때 이름, 자료형, 모양을 모두 확인하고, 다르면 그 모델을 쓰지 않는다.

| 입력 | 모양 | 내용 |
|---|---|---|
| `p1_board` | `[N, 24, 10]` | P1 보드. 3.1과 같은 방법이다(채워진 칸 1.0, 빈칸 0.0, 0행이 맨 위, 칸 종류는 구분하지 않음) |
| `p1_features` | `[N, 52]` | P1 특징 (9.4) |
| `p2_board` | `[N, 24, 10]` | P2 보드 |
| `p2_features` | `[N, 52]` | P2 특징 |

### 9.4 `p1_features`, `p2_features`: float32 `[N, 52]`

| 위치 | 개수 | 값 |
|---|---|---|
| 0 ~ 6 | 7 | `current` 원-핫 (`I J L O S T Z` 순서) |
| 7 ~ 41 | 35 | `queue`의 앞 5칸을 칸마다 7개 원-핫으로. 칸 `k`(0~4)의 블록이 `I J L O S T Z` 중 `j`번째(0~6)면 `[7 + 7k + j] = 1`. 블록이 없는 칸은 7개 모두 0 |
| 42 ~ 48 | 7 | `hold` 원-핫. 비었으면 모두 0 |
| 49 | 1 | `combo + 1` (콤보가 없으면 0) |
| 50 | 1 | `b2b`면 1, 아니면 0 |
| 51 | 1 | `pending` |

- 3장의 공통 규칙을 그대로 따른다. 모든 값은 **정수를 그대로 float32로 바꾼 것**이고, 나누기 같은 정규화와 보드 통계는 **모델 안에서** 계산한다. Java와 Python의 입력이 비트 단위로 같아야 하기 때문이다.
- 형식 2의 `features`(3.2)와는 배치가 다르다. 결정 시점의 상태에는 `current`가 있고, 배치의 결과인 `lines`, `attack`은 없다.
- 미리보기는 늘 5개이지만, 5개보다 적으면 빈 칸을 0으로 둔다(3.2와 같은 방법). 5개보다 길게 알고 있으면 앞 5개만 넣는다(두 인코더 모두 5개보다 많으면 거부한다).

### 9.5 출력, 꼬리표, 내보내기

- 출력 `p1_win`: float32 `[N, 1]`(정확히 이 모양). 0 이상 1 이하의 확률이며, 시그모이드까지 모델 안에서 계산한다.
- 꼬리표는 5장의 키를 그대로 쓴다.

| 키 | 필수 | 값 |
|---|---|---|
| `tetris.model_io` | 필수 | `winprob-1` |
| `tetris.rules` | 필수 | 학습 자료의 규칙 버전 `0.3`. Java의 규칙 버전과 같아야 한다 |
| `tetris.stage` | 선택 | 학습 실행 이름 (예: `wp01`) |
| `tetris.description` | 선택 | 사람이 읽는 설명 (학습 자료 요약 등) |

- 가치 모델과는 `tetris.model_io`로 구분된다. `OnnxScorer`는 승률 모델을, `WinRate`는 가치 모델을 거부한다.
- 내보내기는 6장과 같다. ONNX opset 17, 입력 이름 네 개와 출력 이름 `p1_win`, `N` 축은 모두 dynamic axis이고, `[N, 1]` 모양을 유지한다. 내보낸 뒤 onnxruntime으로 불러 PyTorch와 같은 값인지(차이 1e-5 이내) 확인한다.
- 파일 이름: `winprob_<실행 이름>.onnx` (예: `winprob_wp01.onnx`).

### 9.6 Java (`ai.WinRate`)

- 불러올 때 꼬리표(`winprob-1`, 규칙 버전)와 입력·출력의 이름·자료형·모양을 확인하고, 다르면 예외를 던진다. 게임은 그때 승률 막대를 숨긴다.
- 상태는 `ai.PlayerState`(9.2의 항목, 불변)로 넘긴다. `PlayerState.of(GameModel)`로 게임 스레드에서 복사해 두면 다른 스레드에서 확률을 계산해도 된다. `WinRate` 객체 하나를 여러 스레드가 함께 써도 된다.
- `PlayerState.of(GameModel)`는 읽기만 하는 것처럼 보이지만, 미리보기를 채우느라 게임의 가방을 진행시킬 수 있다(`GameModel.preview()`). 그래서 다른 스레드가 같은 게임을 쓰거나 읽는 동안 부르면 안 되고, 게임을 진행하는 스레드에서 부른다. `GameModel` 두 개를 받는 메서드도 같다.
- `GameModel` 두 개를 바로 넘기는 메서드는, 어느 한쪽이라도 끝났으면 모델을 부르지 않고 결과를 돌려준다(P1 승 1, P2 승 0, 둘 다 끝남 0.5).

### 9.7 검증 (공통 픽스처)

[fixtures/winprob/](../fixtures/winprob/)에 시험용 모델과 사례 파일이 있다. 사례 형식은 [FIXTURES.md](FIXTURES.md) 5.11이다.

| 파일 | 내용 |
|---|---|
| `winprob_linear.onnx`, `.json` | 가중치를 식으로 정한 선형 모델(`logit = w · (P1 입력 − P2 입력)`, 시그모이드). 손으로 확인할 수 있는 값과 인코딩 사례 |
| `winprob_tiny.onnx`, `.json` | 학습에 쓰는 구조(합성곱, 보드 통계, 자리 대칭 머리)를 아주 작게 만든 모델. Java ONNX Runtime이 실제 모델의 연산을 Python과 같은 값으로 실행하는지 |
| `winprob_linear_wrong_model_io.onnx` 등 | Java가 **거부해야 하는** 모델(`WinRateTest`): 꼬리표의 형식이 `2`, 규칙 버전이 틀림, 출력이 `[N]` |

| 사례 | 확인하는 것 |
|---|---|
| `encode` | 상태 → 보드 텐서와 특징 52개. Java 인코더와 Python 인코더가 같은 값을 만드는지 |
| `encode_record` | 기록 `match-1`의 `state` 객체 그대로 → 같은 텐서. Python 학습 자료를 만드는 경로와 Java가 같은 값을 만드는지. 상태는 Java 대전 러너가 쓴 `fixtures/match/basic.json`에서 가져왔다 |
| `run` | 상태 쌍 여러 개 → `p1_win`. **Python onnxruntime이 계산한 값**을 기대값으로 적고 Java가 같은 값(오차 1e-5 이내)을 내는지 |
| `metadata` | 꼬리표 읽기와 버전 확인 |

Java 쪽은 이에 더해, 대전 기록을 다시 두며 턴마다 `PlayerState.of(GameModel)`의 인코딩이 기록의 `state`로 만든 인코딩과 같은지 확인한다(`WinRateTest`). 그래서 Python이 기록으로 학습한 입력과 Java가 게임 중에 만드는 입력이 같다는 것이 이어서 확인된다.

시험용 모델과 사례 파일은 [python/tools/make_winprob_fixture.py](../python/tools/make_winprob_fixture.py)로 다시 만든다(`winprob_tiny`는 PyTorch가 필요하다).
